  pollers and clients and even use webhooks in the future. I would like to

  that I would be able to add new implementations more easily in the future.    

● There's a meaningful design choice here before I touch anything. The key
  question is where the mapping from source-specific DTOs to RawEvents lives —
  that determines what the interface contract looks like.

● User answered Claude's questions:
  ⎿  · What should FeedClient return? → Source-specific DTO (FeedClient<T>)
● Your SRP concern is valid. Collection<RawEvent> works when the client and
  domain are tightly coupled by design, but here UsgsFeedClient is purely a
  transport layer — it should know nothing about RawEvent. Forcing mapping into
  it would make each client harder to test and reuse independently.

  The better path is FeedClient<T> + an abstract SourcePoller<T> using the
  template method pattern:

  FeedClient<T>            → only fetches and deserializes the source format
  SourcePoller<T>          → execute() calls fetch → toRawEvents → publishAll
    UsgsPoller<...>        → owns toRawEvents + the @Scheduled method

  The poller stays generic through execute(), but mapping responsibility stays
  in the concrete poller where it belongs. Webhooks don't extend this hierarchy
  at all — they'd just inject RawEventPublisher directly from a controller.

  Shall I proceed with this design?
